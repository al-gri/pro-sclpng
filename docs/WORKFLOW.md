# Работа нескольких чатов

## Роли

Владелец продукта — al-gri: scope, доступ, merge, переход demo/live. Главный чат — Architecture: baseline, ADR, межмодульные споры. Один Integrator: задачи, base SHA, interfaces, review, main. Worker: одна ограниченная задача. QA: независимый review конкретного SHA и тестовые доказательства.

Постоянные специализированные Leads не обязательны на старте. Начать с текущего главного чата, одного Integrator, одного worker и отдельного QA на готовом PR. Market Data/Quant подключаются по зависимости. Role prompt не создаёт агента и не обеспечивает автономную переписку.

## Источник истины

1. Владелец и принятое scope/security решение.
2. Принятые ADR/specs в main.
3. AGENTS и INVARIANTS.
4. Issue с acceptance и allowed paths.
5. Код/тесты конкретной ревизии.

Старые чаты — источник контекста, не способ молча переопределить accepted contract. При конфликте сделать ADR proposal; не стирать старую историю.

## Один цикл

1. Integrator проверяет dependencies, выдаёт task packet и фиксирует scope.
2. Worker читает актуальный main и Issue, проверяет инструменты, пишет claim с base SHA и branch.
3. Работает в отдельной ветке/worktree; не трогает чужие незакоммиченные изменения.
4. Добавляет код, применимые tests и handoff; открывает PR.
5. QA читает diff и пытается воспроизвести negative cases на head SHA.
6. Integrator оценивает контракты/интеграцию; владелец выполняет merge.
7. Открытые риски становятся отдельными Issues; статус закрывается только после принятого результата.

Shared root files изменяются последовательно. Не требовать rebase как ритуал: ветка должна быть совместима с актуальным main и тестироваться; никакого force-push без отдельного разрешения. Достаточно merge main в рабочую ветку при необходимости.

## Stop conditions

Нет доступа к требуемому источнику, неожиданная схема API, изменение контракта, выход за allowed paths, отсутствующий тестовый инструмент. Продолжить независимую часть, явно пометить зависимую BLOCKED. Не замещать факт предположением.

## Что сохраняется

Git: решения/спецификации/код/малые fixtures. Issues: очередь/блокеры. PR: diff/проверки/обсуждение. Handoff: состояние задачи. Большие данные: внешний архив, в Git только manifest/hash. Секреты: не чат и не Git.

## Удаление или замена чата

Безопасно, когда сохранены commits/branch/PR, реальные команды и результаты, решения/ADR, известные ограничения и следующий шаг; уникальных артефактов только в чате нет. Незавершённую работу также можно передать, если branch/patch и BLOCKED handoff сохранены. Удалять чат необязательно.

Главный чат тоже заменяем: новый читает AGENTS, PROJECT_STATE, ARCHITECTURE, INVARIANTS, roadmap, accepted ADR и open Issues. Восстановление без старой переписки — отдельный организационный тест.

## Ограничения проверки

Все чаты могут действовать под одним login. Их отзывы дают раздельные reasoning/reproduction sessions, но не разные GitHub approvals. CI доказывает только проверенные свойства, не прибыльность и не полноту стратегии.
