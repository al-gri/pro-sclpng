## Evidence paraphrases and applicability

### Regular JSON Depth Channel

Applicability: current UTA v3 public regular JSON `books50`; `spot`, `usdt-futures`, `coin-futures`, `usdc-futures`.

The page defines first `snapshot`, subsequent incremental `update`, and two-component ask/bid levels `[price, quantity]`. It labels the second component only as sell/buy quantity.

It does **not** state the quantity asset/unit, define a level deletion operation, define zero as deletion, or state whether zero is legal/illegal in a regular snapshot.

### Best Practices

Applicability: current UTA regular order-book guidance.

The page confirms snapshot then incremental updates and says the system pushes the latest state; multiple short-period changes such as `A -> B -> A` may result in the final state being pushed. This proves final-state/coalescing behavior but does not define the encoding of a removed level.

### Market Data REST / instrument metadata

Applicability: current REST market data only.

Standard REST depth likewise uses `[price, quantity]` without adding a quantity-unit statement. Instrument metadata has futures quantity constraints/multipliers but does not bind their asset semantics to WS depth-level quantity.

### Order Management

Applicability: order requests only, **not** depth levels.

Current order-placement docs define category/order-specific request `qty` units (for example USDT/USDC futures order quantity in base coin and COIN futures order quantity in quote coin). This demonstrates that Bitget quantity semantics can be interface/category sensitive; it is not evidence that a depth quantity uses those units.

### RPI JSON

Applicability: RPI depth only.

RPI levels have three components: price, non-RPI quantity, RPI quantity, with separate profile/sequence semantics. RPI component-zero behavior cannot be imported into regular two-component `books50`.

### SBE

Applicability: UTA SBE binary WS only.

The current SBE intro exposes a separate versioned schema (schema version 5 / semanticVersion 1.0.0) and depth template. It is a different profile; it supplies no regular-JSON zero/delete or quantity-unit guarantee.

## U-09 — separate conclusion

**UNKNOWN / BLOCKED.**

The current regular JSON depth source does not identify quantity as base coin, quote coin, contract count, lot count, or another unit. This remains true for the initial target `usdt-futures`.

It is forbidden to transfer order-placement or public-trade units into depth levels without a depth-specific official statement or an explicitly reviewed engineering/ADR decision.

## U-10 — separate conclusion

**UNKNOWN / BLOCKED.**

The current regular JSON depth source does not define `qty="0"` as a deletion operation and does not document an alternate remove-level marker.

SPEC-001 remains unchanged: the project distinction between `SetLevel(qty>0)` and `DeleteLevel` is not weakened. MD-002 provides no source mapping from regular Bitget zero to `DeleteLevel`.

## What future REC-001E may use

REC-001E may use these evidence-backed facts/boundaries:

- regular JSON `books50` source levels are `[price, quantity]`;
- first push is snapshot; later pushes are incremental updates;
- current regular categories are `spot`, `usdt-futures`, `coin-futures`, `usdc-futures`;
- regular JSON, RPI JSON, and SBE must remain profile-separated;
- RPI three-component quantity semantics cannot normalize regular JSON by implication;
- order-request `qty` units cannot be promoted to market-depth units;
- lexical source quantity preservation remains safe, while canonical unit/delete effects stay blocked by U-09/U-10.

## What remains forbidden to assume

- regular depth quantity is base coin, quote coin, contracts, lots, or any other specific unit;
- `usdt-futures` market-depth quantity inherits the order-placement request unit;
- `qty="0"` means remove/delete in regular JSON;
- zero is either allowed or forbidden in a regular snapshot;
- RPI component-zero behavior defines regular JSON behavior;
- SBE deletion/unit/version semantics define regular JSON behavior;
- identical two-component wire shape means all regular categories have one undocumented common unit.
